# DATA-003 — Kamus fisik dan urutan migration Foundation+MVP

**Status:** spesifikasi DDL sebelum implementasi. [DATA-002](mvp-physical-data-design.md) menetapkan ownership dan invariant; dokumen ini menetapkan tipe, nullability, key, seed, dan urutan yang belum eksplisit. SQL baru ditulis bersama slice yang memakai tabel, lalu diuji di PostgreSQL sebelum handler di-merge. Sebelas migration yang sudah ada tetap sumber SQL aktual dan tidak diubah sesudah dipakai lingkungan bersama. Angka policy per tenant adalah data aktivasi, bukan konstanta DDL.

## Notasi yang wajib diterjemahkan ke DDL

`U` = `uuid NOT NULL`; `U?` = `uuid NULL`; `S(n)` = `varchar(n) NOT NULL`; `S(n)?` nullable; `D` = `date NOT NULL`; `D?` nullable; `T` = `timestamptz NOT NULL`; `T?` nullable; `N` = `numeric(20,6) NOT NULL`; `N?` nullable; `R` = `numeric(24,10) NOT NULL`; `I` = `integer NOT NULL`; `B` = `boolean NOT NULL`; `J` = `jsonb NOT NULL` dengan JSON Schema/version. `M` dan `A` mengikuti [standar database §2](../engineering/database-standards.md#2-kolom-standar-dan-pengecualian). Domain `status` selalu `S(40)` dengan `CHECK` sesuai state FSD; `currency` `char(3)` dengan ISO validasi aplikasi dan `CHECK` format. Semua tabel tenant scope punya `(tenant_guid,id)` unique; entity scope punya `(tenant_guid,legal_entity_guid,id)` unique untuk composite FK lokal. Semua `*_id` FK lokal same scope, semua `*_guid` referensi owner lain tanpa FK SQL. Pengecualian: `guid` identitas row dan metadata aktor tetap UUID. JSON `content_json` policy tervalidasi terhadap schema versi sebelum commit, bukan field bebas.

**Aturan umum:** waktu efektif `[from,to)` (`to` eksklusif, NULL = tak terbatas); code dan nomor dokumen yang pernah terbit tak didaur ulang; unique permanen termasuk row soft-deleted. Untuk master draft yang belum pernah terbit, unique aktif boleh partial tetapi alias code lama tetap disimpan saat publish. Semua jumlah uang/qty yang tidak boleh negatif memakai `CHECK >=0`; sign reversal disimpan pada `direction`/movement leg, bukan angka negatif bila tabel sumber tidak mendukung. Audit, idempotency, outbox, inbox memakai migration runtime per owner. `deleted_at/by` hanya untuk draft yang benar-benar boleh dihapus; posted/history tidak punya delete runtime. Indeks list minimal `(tenant_guid,legal_entity_guid,status,business_date DESC,id DESC)` jika business date ada, atau `(tenant_guid,legal_entity_guid,status,created_at DESC,id DESC)`; kebutuhan lain diuji `EXPLAIN` pada fixture ukuran pilot sebelum ditambah.

**Kompatibilitas SQL awal:** `accounting.journals/journal_lines` pada migration `000001` hanya menyimpan jurnal POSTED, sehingga API manual journal `DRAFT→APPROVED→POSTED` wajib memakai tabel draft baru. Root `guid` dipakai kembali pada row posted; draft tetap menjadi histori, dan `GET` menggabungkan view logis berdasarkan GUID tanpa duplikasi. POST tidak mengubah row posted. `accounting.accounts` awal belum punya status DRAFT, currency atau unique code permanen: migration `000002` menambah kolom/constraint secara expand dan memperkenalkan alias code sebelum menghapus partial index lama; data yang pernah published tidak boleh kehilangan identitas. `fiscal_periods.period_end` pada SQL awal inklusif, berbeda dari effective interval policy `[from,to)`; jangan menyamakan kedua semantik. `purchase.purchase_orders.currency_code = IDR` sengaja untuk pilot satu currency; dukungan mata uang baru membutuhkan migration dan policy FX terpisah. Ini semua pekerjaan migration yang **sudah dirancang**, bukan perilaku yang boleh diasumsikan berjalan di SQL awal.

## Migration, seed, dan bukti sebelum handler

| Tahap | Perubahan DDL/data | Verifikasi minimum sebelum handler |
|---|---|---|
| P1 Platform org/IAM | tenant/entity/role/member/session/invite + policy/numbering | hierarchy cycle, overlapping grant, token hash uniqueness, admin delegation, revoke ≤60 s |
| P2 Platform master | party/account/address/alias/sensitive proposal + SKU/UOM migration awal | entity composite FK, duplicate code/alias, masked sensitive, 1 carton=12 pcs snapshot |
| P3 Commercial | SO/credit/requisition + PO migration awal/amendment | two submit same key, two credit writers, revision release ack, PO amendment vs GRN |
| P4 Operations | receipt/stock migration awal + lot/serial/reservation/adjustment/pick/pack/delivery/POD | 100 writers on 10 stock, serial uniqueness, source leg dedup, 3+1+1 POD balance |
| P5 Finance | invoice/open item/payment/tax document + GRNI/journal migration awal + COA/rule/close | invoice+journal atomicity, two allocations on one open item, reversal, trial balance, close watermark |
| P6 Platform jobs | import/row/external registry/attachments/notification/report | 100 row/3 error, object quarantine, scope revoke, report expiry/export audit |

Seed sintetis deterministik: tenant `T`, company `C`, legal entities `E-A/E-B`, branch/warehouse `B-A/W-A`, users `sales/buyer/receiver/approver/controller/security`, service principals per owner, customer `CUS-1` pada dua entity, vendor `VEN-1` pada E-A, SKU `SKU-1` pcs dan carton 1:12, open periods dan policy versions aktif pada E-A. Simpan GUID fixture stabil di test package, bukan kode produksi; semua date relatif terhadap `business_date` fixture sehingga tes tidak bergantung jam komputer. Seed environment produksi hanya katalog role/permission dan konfigurasi kosong; **tidak** membuat policy finansial aktif tanpa sign-off owner. Opening balance diimpor melalui command khusus dengan source registry dan rekonsiliasi, bukan SQL bebas.

Setiap migration baru mencatat expand/backfill/contract, lock budget, `NOT VALID`/validasi bertahap bila volume perlu, indeks berdasarkan query, rollback untuk skema kosong atau forward-fix bagi data posted, checksum, dan restore marker.
